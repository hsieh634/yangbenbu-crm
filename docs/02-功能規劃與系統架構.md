## 1. 使用者與角色

| 角色 | 代碼 | 主要工作 | 主要使用介面 |
|---|---|---|---|
| 管理者 | `ADMIN` | 診所設定、帳號與權限、報表、方案與價目 | 後台（桌機） |
| 醫師 | `DOCTOR` | 看診、辨證、開立調理方案、檢視問卷與健康數據 | 後台（桌機／平板） |
| 櫃檯 | `FRONT_DESK` | 預約、報到、批價、療程扣堂、領藥登記 | 後台（桌機） |
| 診務人員 | `CLINICAL_ASSISTANT` | 針灸、推拿等療程執行，看板推進 | 後台（平板） |
| 健康管理師 | `HEALTH_MANAGER` | 問卷追蹤、診後關懷、生活型態指導、追蹤任務 | 後台（桌機） |
| 病患 | `PATIENT` | 預約、填問卷、看養本簿、收提醒 | LINE LIFF（手機） |

## 2. 前端功能規劃

前端分成兩個介面，由同一個 Next.js 專案以 route group 區分：

- **診所後台** `/(staff)/...`：桌機和平板優先，資訊密度高
- **病患端** `/(liff)/...`：在 LINE 內開啟，手機優先，介面簡潔

### 2.1 診所後台

#### A. 共用框架
- 登入（帳號密碼 + TOTP 兩步驟驗證）、忘記密碼、閒置自動登出
- 側邊選單依角色顯示不同項目
- 全域病患搜尋（姓名、電話、病歷號、身分證末四碼），快捷鍵 `/`
- 通知中心：新預約、問卷已填、追蹤任務到期
- 切換診所（連鎖院所的帳號可能屬於多家）

#### B. 今日看板（首頁）— 需求 4
- 欄位依就診狀態分欄：**已預約 → 已報到 → 候診 → 看診中 → 療程中 → 待批價／領藥 → 已完成**
- 卡片內容：病患姓名、預約時段、醫師、療程名稱與剩餘堂數、標籤（初診、過敏、VIP）、等候時間
- 拖曳卡片或點按鈕推進狀態；每次推進都會記錄由誰在什麼時間操作
- **交接備註**：卡片上可留言給下一個職務（例如「左肩針灸後請熱敷 10 分鐘」）
- 依醫師、診間篩選；即時同步，多台裝置同時看
- 上方統計：今日預約數、到診率、平均等候時間

#### C. 病患管理 — 需求 1
- 病患列表：搜尋、篩選（標籤、負責健管師、療程狀態、最後回診日）、分頁
- 新增／編輯病患：基本資料、聯絡方式、緊急聯絡人、過敏史、既往病史、來源管道、標籤、**個資同意書狀態**
- **病患 360° 頁面**（分頁籤）：
  - 總覽：基本資料、體質雷達圖、進行中的療程與剩餘堂數、下次預約、待辦追蹤
  - 就診紀錄：時間軸
  - 問卷與健康數據：歷次問卷結果、體重／血壓／睡眠趨勢圖
  - 調理方案：目前方案與歷史方案
  - 療程與領藥：購買的療程、每次扣堂紀錄、領藥紀錄
  - 追蹤紀錄：電話或 LINE 關懷紀錄、追蹤任務
  - 稽核紀錄：誰看過或改過這位病患（僅管理者可見）
- 合併重複病患（管理者）

#### D. 預約管理 — 需求 1
- 行事曆：日、週檢視，依醫師或診間分欄
- 新增預約：選病患 → 選醫師／服務項目 → 選時段（只顯示可預約的時段）
- 預約狀態：已預約、已確認、已報到、未到、取消、改期
- 排班設定：醫師門診時段、休診、每時段可約人數
- 未到紀錄（No-show）統計

#### E. 就診服務紀錄 — 需求 1
- 報到後建立就診單
- 醫師填寫：主訴、四診摘要、證型、治則、醫囑（自由文字 + 常用片語）
- 本次服務項目：看診、針灸、推拿、拔罐……（勾選後自動扣療程堂數）
- 註記：本系統只做服務紀錄，**正式病歷與健保申報仍在 HIS**；可填 HIS 就診序號以便對照

#### F. 問卷與健康數據 — 需求 2
- 問卷範本管理（管理者）：題目編輯器，支援單選、多選、量表、數字、文字；可設定計分規則
- 內建範本：體質問卷（九種體質）、生活型態問卷（睡眠、飲食、運動、壓力）
- 發送問卷：現場平板填寫，或推播 LINE 連結請病患自行填寫
- 結果檢視：體質分數雷達圖、與上次比較
- 健康數據登錄：體重、血壓、體脂、睡眠時數等，可由病患在 LIFF 自行記錄

#### G. 調理方案 — 需求 2
- 方案範本：例如「失眠調理 8 週」，內容包含療程建議、飲食宜忌、作息建議、追蹤節點
- 依範本為病患建立個人化方案，可調整內容
- 方案狀態：草稿 → 執行中 → 已完成／中止
- 方案發布後同步到病患的養本簿

#### H. 療程與領藥 — 需求 3
- 療程方案設定（管理者）：名稱、包含堂數、有效期限、價格
- 為病患開立療程：購買日期、到期日、剩餘堂數
- 扣堂：就診時勾選服務項目自動扣，或手動扣堂並寫原因；可沖銷
- 到期提醒：剩餘 1 堂或 30 天內到期
- 領藥紀錄：藥品或處方名稱、天數、領取日期、下次可領日期（**處方內容以 HIS 為準**，這裡只記錄領取狀況）

#### I. 診後追蹤 — 需求 6
- 追蹤任務清單：今日待辦、逾期、已完成；可依負責人篩選
- 自動產生任務：依調理方案的追蹤節點（例如療程後第 3 天電話關懷）
- 關懷紀錄：聯絡方式、內容、病患回饋、下次追蹤日
- LINE 訊息範本管理與發送紀錄

#### J. 報表（管理者）
- 營運：每日預約數、到診率、未到率、各醫師看診數
- 療程：銷售數、扣堂數、未使用堂數（預收款負債）
- 回診率：30、60、90 天回診率
- 追蹤：任務完成率、逾期數
- 所有報表可匯出 CSV

#### K. 系統設定（管理者）
- 診所資料、營業時間、診間
- 員工帳號、角色指派、停用
- 服務項目、療程方案、問卷範本、LINE 訊息範本
- LINE 官方帳號設定（Channel ID／Secret）
- 資料匯出：全部資料匯出為 CSV 與 FHIR Bundle
- 資料匯入：從 HIS 匯入病患 CSV

### 2.2 病患端（LINE LIFF）

| 頁面 | 功能 |

| 療程與領藥 | 剩餘堂數、到期日、下次可領藥日 |

## 3. 後端功能規劃

### 3.1 模組劃分（模組化單體）

後端是一個服務，內部依業務領域切模組。每個模組有自己的 controller、service、DTO，模組之間只透過 service 介面呼叫，未來需要時可以拆分。

| 模組 | 職責 | 主要 API（`/api/v1`） |
|---|---|---|
| `auth` | 員工登入、TOTP、Session、病患 LINE Login | `POST /auth/login`、`POST /auth/totp/verify`、`POST /auth/line` |
| `tenancy` | 診所、診間、營業時間 | `GET/PATCH /clinic` |
| `staff` | 員工帳號、角色 | `GET/POST/PATCH /staff` |
| `patients` | 病患 CRUD、搜尋、合併、標籤、同意書 | `GET/POST/PATCH /patients`、`GET /patients/:id/timeline` |
| `scheduling` | 排班、可預約時段計算、預約 | `GET /availability`、`GET/POST/PATCH /appointments` |
| `visits` | 就診單、狀態機、交接備註、看板 | `POST /visits`、`POST /visits/:id/transition`、`GET /board/today` |
| `packages` | 療程方案、購買、扣堂、沖銷 | `POST /patients/:id/packages`、`POST /packages/:id/usages` |
| `medications` | 領藥紀錄 | `GET/POST /patients/:id/dispenses` |
| `questionnaires` | 問卷範本、發送、作答、計分 | `GET/POST /questionnaires`、`POST /questionnaire-responses` |
| `observations` | 健康數據 | `GET/POST /patients/:id/observations` |
| `care-plans` | 調理方案範本、個人方案 | `GET/POST /care-plan-templates`、`POST /patients/:id/care-plans` |
| `follow-ups` | 追蹤任務、關懷紀錄 | `GET/POST/PATCH /follow-up-tasks` |
| `notifications` | 站內通知、LINE 推播、訊息範本 | `GET /notifications`、`POST /line/webhook` |
| `reports` | 統計報表 | `GET /reports/:type` |
| `audit` | 稽核紀錄寫入與查詢 | `GET /audit-logs` |
| `fhir` | TW Core 對應、匯出、唯讀 FHIR API | `GET /fhir/Patient/:id`、`GET /fhir/$export` |
| `integration` | HIS CSV 匯入、外部 API Key | `POST /imports/patients` |

病患端 API 另外放在 `/api/v1/me/*`（例如 `/me/appointments`、`/me/care-plan`），只能存取本人的資料。

### 3.2 橫切機制

| 機制 | 做法 |
|---|---|
| **租戶隔離** | 每個請求從 Session 取得 `clinicId`，寫入 Prisma Client Extension 自動加條件；資料庫層再以 PostgreSQL RLS 防呆（`SET app.clinic_id`） |
| **權限** | 「角色 → 權限」對照表（例如 `patient:read`、`patient:read_sensitive`、`package:deduct`），由 Guard 與 decorator 檢查；回應時依權限遮罩欄位 |
| **稽核** | Interceptor 自動記錄所有病患資料的讀寫：誰、何時、IP、動作、資源、病患 ID；資料表只能新增 |
| **驗證** | Zod schema 前後端共用；後端入口統一驗證 |
| **錯誤格式** | RFC 9457 Problem Details |
| **API 文件** | 由 Zod 產生 OpenAPI，前端用產生的型別呼叫 |
| **併發控制** | 扣堂、預約時段使用資料庫交易 + 列鎖，避免重複扣堂或超額預約 |
| **冪等性** | 扣堂、推播等寫入 API 支援 `Idempotency-Key` |
| **加密** | 身分證字號、病史等敏感欄位以 AES-256-GCM 應用層加密；身分證另存 HMAC 雜湊供查詢 |
| **即時更新** | 看板以 Server-Sent Events 推送狀態變更 |

### 3.3 背景工作（Worker）

| 工作 | 觸發 | 說明 |
|---|---|---|
| 預約提醒 | 每日排程 | 隔天有預約的病患發 LINE 提醒 |
| 未到標記 | 每日排程 | 預約時間過後未報到的標記為未到 |
| 療程到期提醒 | 每日排程 | 剩 1 堂或 30 天內到期 |
| 領藥提醒 | 每日排程 | 到下次可領藥日時提醒 |
| 追蹤任務產生 | 事件（方案發布、就診完成） | 依方案的追蹤節點建立任務 |
| LINE 推播發送 | 佇列 | 失敗重試、速率限制、記錄發送結果 |
| 報表彙總 | 每日夜間 | 預先計算統計數據 |
| 資料匯出 | 使用者觸發 | 產生 CSV／FHIR Bundle，完成後通知下載 |

### 3.4 核心狀態機

**就診（Visit）— 看板的資料來源**

```
SCHEDULED ─報到→ CHECKED_IN ─→ WAITING ─→ IN_CONSULTATION ─→ IN_TREATMENT ─→ PENDING_CHECKOUT ─→ COMPLETED
     │                                          └───────────（無療程）──────────────┘
     └─→ NO_SHOW / CANCELLED
```

每次狀態轉換都寫入 `VisitEvent`（操作人、時間、備註），可以算出各階段等候時間。不允許的轉換由後端拒絕。

**療程扣堂**：`PackageUsage` 只新增不修改；沖銷是新增一筆負數紀錄。剩餘堂數 = 購買堂數 − 使用紀錄總和，所以帳一定對得起來。

**調理方案**：`DRAFT → ACTIVE → COMPLETED / REVOKED`

**追蹤任務**：`OPEN → IN_PROGRESS → DONE / SKIPPED`；過了預定日期仍未完成即視為逾期。

## 5. 資料模型

```
Clinic ─┬─ Staff ── StaffRole
        ├─ Room
        ├─ Schedule（醫師排班）
        ├─ Service（服務項目）
        ├─ PackagePlan（療程方案範本）
        ├─ QuestionnaireTemplate
        ├─ CarePlanTemplate
        ├─ MessageTemplate
        └─ Patient ─┬─ PatientConsent（同意書）
                    ├─ PatientTag
                    ├─ LineBinding
                    ├─ Appointment ── Visit ─┬─ VisitEvent（狀態轉換）
                    │                        ├─ VisitService（本次服務項目）
                    │                        └─ HandoffNote（交接備註）
                    ├─ PatientPackage ── PackageUsage（扣堂紀錄，只新增）
                    ├─ MedicationDispense
                    ├─ QuestionnaireResponse（FHIR JSON）
                    ├─ Observation
                    ├─ CarePlan ── CarePlanActivity
                    └─ FollowUpTask ── CareContact（關懷紀錄）

AuditLog、Notification、OutboundMessage、ImportJob（全系統共用）
```

設計原則：
- 每張業務表都有 `clinicId`、`createdAt`、`updatedAt`、`createdBy`
- 病患相關資料**軟刪除**（`deletedAt`），符合病歷保存年限
- 主鍵使用 UUID v7（有時間順序，便於索引，且不會洩漏筆數）
- FHIR 相關資料（問卷作答）以 JSONB 儲存原始結構，另抽出計分結果欄位供查詢

## 6. 技術架構

### 6.1 架構決策：前後端分離 + 模組化單體

比起 [01 文件](01-技術選型研究.md) 原先規劃的 Next.js 全端單一專案，改為**前後端分離**，理由：

1. **API 優先**：這套系統要被 LINE、HIS 廠商、未來的 App 與 FHIR 用戶端呼叫，獨立的 API 服務比較清楚
2. **背景工作與 Webhook**：推播排程、LINE Webhook、匯入匯出這類長時間工作，適合跑在常駐的後端，而不是 Serverless
3. **作品集展示**：前端與後端各自的設計能力都看得出來
4. 以 **monorepo** 管理，前後端共用型別與驗證規則，維持一人開發的效率


### 6.3 技術棧

| 層級 | 技術 | 選擇理由 |
|---|---|---|
| Monorepo | pnpm workspaces + Turborepo | 前後端共用套件、快取建置 |
| 語言 | TypeScript（strict） | 全端同一種語言 |
| **前端框架** | Next.js（App Router）+ React | 後台與 LIFF 共用元件；SSR 讓 LIFF 首屏更快 |
| UI 元件 | Tailwind CSS + shadcn/ui | 後台介面快速且一致；可客製診所品牌色 |
| 資料抓取 | TanStack Query | 快取、樂觀更新（看板拖曳） |
| 表單 | React Hook Form + Zod | 與後端共用驗證規則 |
| 表格 | TanStack Table | 病患列表、報表 |
| 行事曆 | FullCalendar | 預約日／週檢視、資源分欄 |
| 拖曳 | dnd-kit | 看板 |
| 圖表 | Recharts | 體質雷達圖、健康趨勢 |
| LINE | LIFF SDK | 病患端登入與 LINE 內開啟 |
| **後端框架** | NestJS（Fastify adapter） | 模組化結構、Guard／Interceptor 適合做權限與稽核 |
| ORM | Prisma | Schema 易讀、migration 管理 |
| 資料庫 | PostgreSQL 16 | RLS 多租戶、JSONB 存 FHIR、全文搜尋 |
| 佇列與排程 | pg-boss | 用 PostgreSQL 當佇列，不必另架 Redis |
| 認證 | Session cookie（httpOnly）+ TOTP（otplib）；病患用 LINE Login | 後台不用 JWT 存在瀏覽器，降低外洩風險 |
| API 契約 | Zod → OpenAPI（zod-openapi）→ 前端型別 | 單一來源，前後端不會對不上 |
| FHIR | `@types/fhir`（R4）+ 自寫 TW Core mapper | 輕量，不必架完整 FHIR Server |
| 日誌 | pino（結構化日誌，自動遮罩個資欄位） | |
| 測試 | Vitest（單元）、Supertest（API）、Playwright（E2E）、Testcontainers（真實 PostgreSQL） | |
| CI | GitHub Actions：lint、型別檢查、測試、建置 | |
| 本機開發 | Docker Compose（PostgreSQL、MinIO、Mailpit） | 一行指令起環境 |

### 6.4 部署

| 環境 | 前端 | 後端與 Worker | 資料庫 | 用途 |
|---|---|---|---|---|
| Demo（作品集） | Vercel | Render 或 Fly.io（Docker） | Neon／Supabase | 公開展示，假資料 |
| 正式（真實診所） | GCP Cloud Run（asia-east1 台灣） | Cloud Run（asia-east1） | Cloud SQL for PostgreSQL（asia-east1） | 符合資料境內存放原則 |

三個服務都打包成 Docker image，換平台不必改程式。

## 7. 非功能需求

| 項目 | 目標 |
|---|---|
| 效能 | 一般頁面 API p95 < 300ms；看板狀態更新 1 秒內同步到其他裝置 |
| 可用性 | 營業時間 99.5%；每日自動備份，保留 30 天；可還原到任一時間點 |
| 安全 | OWASP Top 10；全站 HTTPS；員工強制兩步驟驗證；閒置 30 分鐘登出 |
| 個資 | 稽核紀錄保留至少 7 年；日誌不得出現身分證、電話等個資 |
| 可攜性 | 診所可隨時匯出全部資料（CSV + FHIR Bundle） |
| 裝置 | 後台支援 Chrome、Edge、iPad Safari；LIFF 支援 iOS／Android 的 LINE |
| 無障礙 | 對比度符合 WCAG AA，可用鍵盤操作 |
