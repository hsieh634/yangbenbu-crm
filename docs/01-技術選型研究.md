# 養本簿 CRM：技術選型研究與架構建議

> 研究日期：2026-11-11
> 目的：了解台灣醫療體系目前採用的技術與政策方向，決定「養本簿」診所 CRM 與健康管理系統的架構。

---

## 1. 結論摘要

1. **定位：做 HIS 之上的 CRM／健康管理層，不重做 HIS。** 健保卡讀取、申報、處方、電子病歷這些核心功能交給既有 HIS（健保署補助計畫也要求申請廠商必須是 HIS 核心功能的原廠）。養本簿負責 HIS 沒做好的部分：體質問卷、調理方案、療程堂數、診後追蹤、LINE 互動、跨職務交接。
2. **資料標準：「FHIR-ready」，而不是「FHIR-native」。** 內部用關聯式資料庫（PostgreSQL）支撐 CRM 的日常操作，另外做一層 **TW Core IG（FHIR R4）對應層**，用來匯出資料和對外提供 API。問卷直接採用 FHIR `Questionnaire`／`QuestionnaireResponse` 格式儲存。
3. **部署：雲端 SaaS、多租戶，資料放在台灣境內。** 2022 年修正的電子病歷辦法已經允許上雲，原則是資料存放在境內；健保署 2025 年起也投入 3 億元補助基層診所上雲。
4. **資安與個資：一開始就內建。** 個資法 2025 年修正後，個資事故必須通報。系統一開始就要有稽核紀錄、欄位層級權限、敏感欄位加密和資料可攜（匯出）。

---

## 2. 台灣醫療資訊現況

### 2.1 FHIR 與 TW Core IG：國家級互通標準

- 衛福部以 **FHIR R4（4.0.1）** 為核心，制定 **臺灣核心實作指引 TW Core IG**（目前 v1.0.0）。([TW Core IG](https://twcore.mohw.gov.tw/ig/twcore/))
- 次世代數位醫療平台的分階段時程：2025 年完成醫學中心試驗性互通，**2026 年醫學中心全面串接，2027 年擴及區域與地區醫院，2028 年納入衛生所與診所**。([安可人生](https://www.ankecare.com/article/4365-2026-05-21-02-09-32)、[GeneOnline](https://geneonline.news/fhir-taiwan-2025/)、[衛福部資訊處](https://blog.mohw.gov.tw/459/))
- 目前以健保給付鼓勵為主，不採法律強制。([Yahoo 新聞](https://tw.news.yahoo.com/%E8%A1%9B%E7%A6%8F%E9%83%A8%E6%8E%A8%E5%8B%95fhir%E6%A8%99%E6%BA%96-%E5%85%88%E4%B8%8D%E7%BD%B0-%E4%BB%8A%E5%B9%B4%E5%8A%9B%E6%8B%9A%E9%86%AB%E5%AD%B8%E4%B8%AD%E5%BF%83%E9%9B%BB%E5%AD%90%E7%97%85%E6%AD%B7%E5%85%A8%E9%9D%A2%E4%BA%92%E9%80%9A-111110331.html))
- 衛福部已建置 **SMART on FHIR**（OAuth 2.0／OpenID）授權機制，並推出國家級 App 市集 **Taiwan Health App Space（THAS）**，2025 年 10 月辦理 SMART App 上架徵件。([衛福部](https://mohw.gov.tw/cp-101-84198-1.html)、[iThome 李建璋專文](https://www.ithome.com.tw/guest-post/174905))

**對本專案的意義：** 診所預計 2028 年納入 FHIR 互通，現在設計的系統會在那之前上線。資料模型若一開始就能對應到 TW Core，日後與 HIS、醫院或 THAS 串接的成本會低很多。這也是很好的賣點。

### 2.2 電子病歷上雲：法規已開放

2022 年 7 月修正「醫療機構電子病歷製作及管理辦法」，重點如下：([衛福部公告](https://mohw.gov.tw/cp-16-70574-1.html)、[iThome](https://www.ithome.com.tw/news/151994)、[INSIDE](https://www.inside.com.tw/article/28368-epic-cloud))

- 可以委外建置，也可以使用雲端服務；必須簽訂書面契約
- **雲端資料原則上存放於境內**，存放境外需經主管機關核准
- 必須有傳輸加密、安全事故處理機制，以及服務終止時的資料移轉機制

### 2.3 健保署推動基層診所上雲

- 「基層醫療院所資訊服務系統雲端轉型補助計畫」自 2025 年起推動，為期三年，總經費 3 億元。首年已有 771 家西、中、牙醫診所與藥局導入，功能包含電子處方箋、電子病歷、**線上預約**、通訊診療。([CIO Taiwan](https://www.cio.com.tw/121897)、[經濟日報](https://money.udn.com/money/story/5635/9766552)、[計畫書 PDF](https://www.nhi.gov.tw/ch/dl-92533-5bab7ebaf2ae4373acc1f77af40881ad-1.pdf))
- 計畫要求：電子病歷採 FHIR 標準、**院所可免費自行完整下載資料**、具備權限管理機制。
- 申請補助的廠商必須是 HIS 核心功能原廠，但線上預約、電子病歷等功能**可以由代理或串接的其他廠商提供**。([健保署說明](https://www.nhi.gov.tw/ch/dl-82518-009d9caf448b4a7e8f08f58548fc54b5-1.pdf))

**對本專案的意義：** 養本簿不會是補助主體，但可以作為 HIS 廠商的**串接夥伴**，負責預約、會員、追蹤功能。這條路比自己做 HIS 更實際。

### 2.4 LINE 是診所與病患互動的主要管道

- 台灣醫療資訊暨安全協會（服務超過 85% 的基層診所）已與廠商合作，以 LINE 官方帳號整合掛號、候診進度、關懷推播與線上支付，**且不改變醫師既有的 HIS 操作習慣**。([科技新報](https://finance.technews.tw/2025/01/16/his/))
- 診所端的回饋是：希望 LINE 提醒能顯示回診原因與要做的檢查，而不只是單純提醒。([研華專訪](https://www.advantech.com/zh-tw/resources/industry-focus/從缺工困境到智慧醫療：內科診所的數位突圍))

**對本專案的意義：** 病患端以 LINE LIFF 為主，不另外開發 App。提醒內容要個人化（例如「第 6/10 次針灸」「記得帶上週的睡眠紀錄」），這正是「養本簿」的差異化重點。

### 2.5 個資法 2025 年修正

- 2025 年 11 月公布部分條文修正，施行日期由行政院另定。**符合一定範圍的個資事故必須通報個資保護委員會**，並採取應變措施、保存紀錄；也不能再以事故尚未查明為由延遲通知當事人。新增第 20-1 條，要求非公務機關辦理安全維護事項。([理律法律事務所](https://www.leeandli.com/TW/NewslettersDetail/7532.htm)、[INSIDE](https://www.inside.com.tw/article/39958-personal-data-protection-law-differentiated-regulation)、[全國法規資料庫](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=i0050021))
- 病歷、醫療、健康檢查屬於特種個資（第 6 條），原則上不得蒐集處理，必須符合法定例外。

**對本專案的意義：** 稽核紀錄（誰在什麼時候看了或改了哪位病患的資料）、事故應變流程、資料最小化，都要列為第一期就具備的功能。

## 3. 架構選項比較

| 方案 | 說明 | 優點 | 缺點 | 適合 |
|---|---|---|---|---|
| A. 傳統關聯式 CRM | PostgreSQL + 自訂資料表 | 開發快，看板、扣堂等 CRM 邏輯直觀 | 日後要對接 FHIR 需要大改 | 短期專案 |
| B. FHIR-native | 以 FHIR Server（HAPI FHIR、[Medplum](https://www.medplum.com/docs/api)）當主資料庫 | 標準化程度最高，內建 SMART on FHIR | 「剩餘堂數」「今日看板」這類 CRM 概念在 FHIR 裡很彆扭；基礎設施重；TW Core profile 需要另外客製 | 醫院級 EHR |
| **C. 關聯式核心 + FHIR 對應層（建議）** | 內部用關聯式模型，另外做 TW Core 匯出與 API | 開發速度與標準化兼顧；問卷直接用 FHIR 格式 | 需要維護對應程式 | **本專案** |

## 4. 建議架構

### 4.1 系統架構

```
┌────────────── 使用者端 ──────────────┐
│ 診所後台（Web）        病患端（LINE LIFF） │
│ 醫師／櫃檯／診務／健管師／管理者   我的養本簿、預約、問卷 │
└──────────────┬──────────────────────┘
               │ HTTPS
┌──────────────▼──────────────────────┐
│ Next.js 應用（App Router，TypeScript）     │
│  ├ 頁面與 Server Actions                   │
│  ├ 權限層：角色 + 欄位層級 + 租戶隔離         │
│  ├ 領域服務：病患、預約、就診、療程、問卷、追蹤  │
│  ├ 稽核紀錄（所有讀寫病患資料的動作）          │
│  └ FHIR 對應層：/fhir/* API（TW Core R4）     │
└───┬──────────────┬──────────────┬────┘
    │              │              │
┌───▼────┐   ┌─────▼─────┐   ┌────▼───────────┐
│PostgreSQL│   │ 背景工作佇列 │   │ 外部整合           │
│ + RLS 租戶│   │（pg-boss）  │   │ LINE Messaging API │
│ 隔離     │   │ 提醒、排程   │   │ HIS（CSV／API 匯入）│
└────────┘   └───────────┘   └────────────────┘
```

### 4.2 技術棧

| 層級 | 選擇 | 理由 |
|---|---|---|
| 語言 | TypeScript（前後端統一） | 一人開發效率高，型別安全 |
| 框架 | Next.js（App Router） | 後台與 LIFF 共用同一套程式；作品集辨識度高 |
| UI | Tailwind CSS + shadcn/ui | 後台介面開發快，風格一致 |
| 資料庫 | PostgreSQL | 醫療業主流；Row-Level Security 可做多租戶隔離；JSONB 可存 FHIR 問卷 |
| ORM | Prisma | Schema 清楚易讀，migration 管理方便 |
| 認證 | Auth.js（員工帳密 + MFA）、LINE Login（病患） | 員工與病患分開認證 |
| 背景工作 | pg-boss（以 PostgreSQL 當佇列） | 不需要另架 Redis，提醒排程夠用 |
| 測試 | Vitest（單元測試）、Playwright（E2E） | |
| 部署 | Docker 化；Demo 放 Vercel + 雲端 PostgreSQL；正式環境放 **GCP 台灣區域**（asia-east1） | 符合資料境內存放原則 |

### 4.3 模組與 FHIR 資源對應（TW Core）

| 養本簿模組 | 內部資料表 | FHIR R4 資源 |
|---|---|---|
| 病患建檔 | `Patient` | `Patient`（TW Core Patient） |
| 醫師、員工 | `Staff` | `Practitioner`、`PractitionerRole` |
| 預約 | `Appointment` | `Appointment` |
| 就診紀錄 | `Visit` | `Encounter` |
| 體質／生活型態問卷 | `QuestionnaireTemplate`、`QuestionnaireResponse`（JSONB） | `Questionnaire`、`QuestionnaireResponse` |
| 健康數據（體重、血壓、睡眠） | `Observation` | `Observation`（TW Core Vital Signs） |
| 調理方案 | `CarePlan` | `CarePlan` |
| 療程與剩餘堂數 | `TreatmentPackage`、`PackageUsage` | `ChargeItem`／擴充欄位（CRM 專屬，不強求對應） |
| 藥品領取 | `MedicationDispense` | `MedicationDispense` |
| 診後追蹤任務 | `FollowUpTask` | `Task`、`CommunicationRequest` |
| 今日看板 | `Visit.status` 狀態機 | `Encounter.status`（衍生） |

### 4.4 資安與個資設計（第一期就要有）

- **租戶隔離**：每筆資料都有 `clinicId`，並以 PostgreSQL RLS 強制隔離
- **角色權限（RBAC）+ 欄位遮罩**：例如櫃檯看得到電話，但看不到問卷內容與診斷
- **稽核紀錄**：只能新增、不能修改，記錄誰、何時、對哪位病患、做了什麼
- **敏感欄位加密**：身分證字號、病史欄位做應用層加密；身分證另存雜湊值供查詢
- **員工 MFA**、登入失敗鎖定、Session 逾時
- **資料可攜**：診所可一鍵匯出全部資料（CSV + FHIR Bundle），呼應健保署計畫要求
- **事故應變**：提供異常存取告警與匯出紀錄，支援個資法事故通報

## 6. 需要與診所進一步釐清的事項

1. 目前使用哪一家 HIS？是否提供 API 或資料匯出？
2. 療程是否涉及預收款或儲值？涉及的話需要考慮發票與退費流程
3. 「健康管理師」是否為醫事人員？可看的資料範圍為何？
4. 病患同意書的取得方式（紙本或線上），以及蒐集目的的告知內容
5. 是否已有 LINE 官方帳號？訊息量方案為何？
6. 單一院所或規劃連鎖？會影響多院區、跨院資料共享的設計
7. 資料保存年限與病患要求刪除時的處理方式（病歷至少保存 7 年）
