# 養本簿 CRM：安全設計

> 版本：Phase 0（2026-11-13）
> 對應法規背景見 [01 技術選型研究](01-技術選型研究.md) 第 2.2、2.5 節（電子病歷辦法、個資法 2025 年修正）。

病患資料屬於個資法的特種個資。設計原則是**多層防護、預設拒絕**：任何一層出錯，下一層仍然擋得住。

---

## 1. 多租戶隔離

一套系統服務多家診所，最嚴重的事故是 A 診所看到 B 診所的病患。

| 層       | 機制                                                                                    | 位置                                            |
| -------- | --------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 應用層   | 每個請求從 Session 取得目前診所，所有病患查詢都經過 `withTenant(clinicId, fn)`          | `packages/db/src/tenant.ts`                     |
| 資料庫層 | PostgreSQL Row-Level Security：只允許存取 `clinic_id = app.clinic_id` 的資料列          | `packages/db/prisma/migrations/*_rls_and_audit` |
| 連線角色 | 應用程式使用非超級使用者、無 BYPASSRLS 的角色；API 啟動時檢查，正式環境不符合就拒絕啟動 | `apps/api/src/common/prisma.service.ts`         |

設計細節：

- `app.clinic_id` 以 `set_config(..., true)` 設定，**只在該交易內有效**，連線回到連線池不會殘留到下一個請求
- 沒設定時 `current_setting` 回傳空值，條件不成立，**一筆都看不到**
- `FORCE ROW LEVEL SECURITY` 讓資料表擁有者也受限
- 寫入時 `WITH CHECK` 阻止把資料寫進別家診所；`clinic_id` 預設取自目前設定，服務層不必手動帶
- 查詢其他診所的病患 ID 回傳 404，與「不存在」相同，不洩漏該 ID 是否存在

## 2. 認證

| 項目             | 做法                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 密碼             | Argon2id（m=19 MiB, t=2, p=1，OWASP 建議值）                                   |
| 帳號列舉         | 帳號不存在時仍執行一次雜湊比對，回應時間與訊息都與密碼錯誤相同                 |
| 暴力破解         | 連續失敗 5 次鎖定 15 分鐘（密碼與驗證碼共用計數）                              |
| 兩步驟驗證       | TOTP（RFC 6238），金鑰加密儲存；記錄最後使用的時間區段，同一組驗證碼不能用兩次 |
| Session          | 隨機 256 位元 token；資料庫只存 SHA-256，資料庫外洩也無法冒用                  |
| 逾時             | 閒置 30 分鐘、最長 12 小時；待驗證狀態只保留 5 分鐘                            |
| Session fixation | 兩步驟驗證通過後換發新 Session，舊的作廢                                       |
| 啟用兩步驟驗證後 | 其他裝置的 Session 全部登出                                                    |
| 強制兩步驟驗證   | `REQUIRE_MFA=true` 時，未設定的員工只能進入設定頁                              |
| Cookie           | `httpOnly`、`SameSite=Strict`、正式環境 `Secure`                               |
| CSRF             | SameSite=Strict + 寫入請求檢查 `Origin`                                        |

前端與 API 同源（Next.js 將 `/api/*` 轉發到後端），所以不需要開放 CORS，cookie 也能使用最嚴格的 SameSite。

## 3. 授權（角色權限）

- 權限以「角色 → 權限」對照表定義（`packages/shared/src/permissions.ts`），前後端共用同一份
- 後端以全域 Guard 檢查：先認證（`AuthGuard`），再檢查權限（`PermissionsGuard`）
- 未標示 `@Public()` 的 API 一律需要登入，避免新增 API 時忘記加保護
- 被拒絕的請求寫入稽核紀錄（`access.denied`），可以發現越權嘗試
- 前端依權限隱藏選單與按鈕，**只是使用體驗**；真正的檢查在後端

權限矩陣見 [02 功能規劃](02-功能規劃與系統架構.md) 第 4 節，並有單元測試確保關鍵規則（例如只有醫師能寫醫師欄位、完整身分證只開放給管理者／醫師／櫃檯）。

## 4. 敏感欄位

以身分證字號為例：

| 儲存                | 用途                                                                              |
| ------------------- | --------------------------------------------------------------------------------- |
| `national_id_enc`   | AES-256-GCM 加密（隨機 IV、含驗證標籤，竄改即解密失敗），格式帶版本號以便金鑰輪替 |
| `national_id_hash`  | HMAC-SHA256（另一把金鑰），用於完整號碼查詢與防止重複建檔                         |
| `national_id_last4` | 末四碼明文，供櫃檯快速搜尋                                                        |

API 回應一律遮罩；要看完整號碼必須呼叫 `POST /patients/:id/national-id/reveal`，需要 `patient:read_national_id` 權限，且每次都寫入稽核紀錄。病患列表的搜尋稽核只記錄搜尋字串的長度，避免身分證字號出現在紀錄中。

## 5. 稽核紀錄

記錄內容：時間、診所、操作人與角色、動作、資源、病患、結果（成功／拒絕／失敗）、IP、User-Agent、Request ID。

- **讀取即記錄**：病患資料的讀取與稽核寫入在同一個交易，稽核失敗就不回傳資料
- **無法竄改**：沒有 UPDATE／DELETE 的 RLS 政策（影響 0 筆）；另有 trigger 拒絕 UPDATE、DELETE、TRUNCATE，即使以繞過 RLS 的角色連線也擋得住
- **租戶隔離**：每家診所只看得到自己的紀錄；登入失敗等不屬於任何診所的事件 `clinic_id` 為空

個資法 2025 年修正要求事故必須通報並保存紀錄，這份稽核紀錄是事故調查的依據。

## 6. 日誌

- 結構化日誌（pino），每個請求有 Request ID，與稽核紀錄可以對照
- 自動遮罩 `cookie`、`set-cookie`、`authorization`、密碼、身分證、驗證碼

## 7. 正式環境檢查清單

- [ ] `DATABASE_URL` 使用非超級使用者角色（API 會檢查）
- [ ] 建議將「執行 migration 的角色」與「應用程式角色」分開，應用程式角色只給 DML 權限
- [ ] `FIELD_ENCRYPTION_KEY`、`FIELD_HASH_KEY` 存放在 Secret Manager，不進版本控制
- [ ] `COOKIE_SECURE=true`、`REQUIRE_MFA=true`
- [ ] `WEB_ORIGIN` 設為正式網域
- [ ] 資料庫與備份位於台灣境內（電子病歷辦法），開啟時間點還原
- [ ] 登入 API 前加上 IP 速率限制（WAF 或反向代理）
